# Native launcher and scope-observer qualification boundary

The source entry points are entry.preparation, entry.reference and entry.complete.
They are callable by the separately qualified launcher. There is no scientific
execution command enabled by this build-only packet.

The exact qualification record is content-pinned and source/generation-bound.
All nine policy.GAPS require original qualified evidence, not candidate assertions.
Bindings include the exact launcher executable/source, protected scope observer,
complete model/tokenizer/runtime body identities, clock/atlas/alignment and rights,
input manifests, private roots, finite preparation/administration/report profiles,
per-role worker allocations, provider/model/decoding/prices/monetary cap and
independent reviewer identities. Missing bindings refuse execution.

The launcher receives role, programme capsule, request artifact and a complete
read-only/private-output mount allowlist. It restores the programme's logical
relative files in an exclusive namespace, executes its declared entrypoint and
FIT/INFER request, and captures all output/state files with exact relative
path/byte/hash/mode identities and inverse namespace mapping. Participant state
is opaque to the controller and is never unpickled there. Reference state is
safe JSON+NPY1 with complete shape/dtype/array pin checks. A fresh inference
context receives only its exact state and allowed query feature support.

Native driver output is distinct from participant output. Only the protected
driver channel can supply original waits, descendant waits, isolated mounts,
actual accounting and original resource closure. It must bound inherited FDs,
all network except the selected metered author gateway, whole process tree,
wall/CPU/memory, read/write effects and permanently counted attempts. The source
checks the driver return against the exact original request and qualification.
No result stream can self-certify these facts.

Worker read/write/creation/child capacity is reserved in the shared parent pool
before birth. Child acknowledgements settle those same reservations; missing or
unknown results retain possible effects and block closure. Failed attempts
remain counted. Every returned pipe is owned before selector initialization;
cleanup attempts are independent, and original wait/first errors survive.

An observer is started by the trusted allocator before its budget's active start.
Its close interface receives the scope snapshot and final effect boundary and
must return the same scope, full original time coverage, complete tree including
controller, known peak memory, complete syscall/SDK/descendant cost dimensions,
no unknown intervals, zero remaining owned FDs and all original waits. The outer
owner separately accounts transporting that closure and all administration.
This native interface is an explicit unqualified dependency, not a mock production
implementation. Invented observer objects exist only in tests.

The trusted setup bank is charged once; case R1 owners are charged once across
nine consumers. Marginal participant profiles cannot consume bank states or
predictions. The final result carries exact cost-owner identities, consumer joins,
report publication and actual outside closure. It is incomplete without the
qualified outer launcher's original completion.


## S2 concrete source-owned file transport

`Runtime._assets` reads the qualification's finite `runtime_assets` list. Each
item has exactly `source_root`, `source`, `destination`, and `roles`. The source
root is an explicitly selected absolute root; source and destination are exact
path/byte/SHA/mode descriptors with identical bytes and hash. The destination is
immutable (0400/0444, or 0500 for executable source). No search, downloaded body,
registry lookup, symlink, content-derived path guess, or implicit source default
is used. Every selected read, write, directory attempt, FD and readback is charged
to the original active case/participant pool; repeated invocation reauthenticates
its existing assets without creating a new budget or clock.

`launcher.path` is the relative path of `launcher.executable_descriptor` and must
match it exactly. That executable and every explicit `launcher.dependencies`
member must be in the role's selected asset set. The actual process argv uses the
materialized absolute executable, and its cwd is the owning root. The complete
native interpreter/image/runtime remains an independently qualified dependency.
This source construction does not invent executable/native bodies or certify
that external environment by listing its files.

A programme capsule has exactly `files`, `entrypoint`, and `context`. `files` maps
logical relative source paths to exact immutable source descriptors; the first
entrypoint item must be a captured logical file. For reference operations the
capsule and every source file must belong to the explicit reference-role assets.
Participant capsules are the actual captured submissions. No bank source assets
are materialized in participant pools. The reference capsule must include all
source imports needed by its declared entrypoint; compatible external libraries
remain pinned qualification dependencies, never guessed fallbacks.

Before birth, `Runtime._prepare` creates an exclusive per-invocation root, a
programme directory and a data directory. Actual `Store.copy_from` restores
logical source files into the programme directory and copies exact allowed
inputs into data. A mount declares `kind=packed`, `opaque`, or `capsule`.
`codec.artifacts` traverses only the safe packed JSON/array-marker grammar and
collects every referenced array descriptor without decoding any array. A state
capsule is an explicit additional reference-inference mount. Opaque participant
state is copied as bytes and never unpickled by the host. Unrelated provenance
paths inside ordinary JSON are not followed. The request itself must be in the
closed allowlist. Each mount records exact host path, guest path, descriptor and
read-only visibility. The launcher enforces those mounts and no broader host
access; it may not infer missing dependencies.

The actual prepared reference envelope binds generation/source/context, the
original parent, owning runtime request, existing staged input directories,
request, worker limits, and a fresh `outputs/<runtime-request-id>` prefix.
`entry.reference` uses that prefix in its original Store: output names are
namespaced BEFORE JSON and array state publication. Thus state-array and receipt
references remain exact without rewriting scientific payloads. Staged directory
admission is explicit, checked as real directories, and cannot adopt an existing
output prefix. FIT and INFER have distinct publication roots even for one context.

The protected driver receipt must return the exact call, prepared mounts, worker
root and input list; original waits, costs and unknown extents; and the COMPLETE
immutable `output_artifacts` list. `entry.reference` supplies its actual Store
creation list before closing its budget. The native participant driver must
capture its finite output set under its reserved worker budget. `Runtime` checks
result descriptor closure before import. It copies every output by exact
size/hash/mode under O_EXCL and records the original and projected identities.
Reference outputs already carry the invocation prefix. Opaque participant files
are mapped by the controller into that same unique prefix; only descriptors in
the returned result are projected, and opaque bodies are unchanged. The next
INFER receives that exact imported state as an explicit input, along with its
packed query closure. No earlier owner is reopened. Failed writes/copies remain
failed original attempts; no partial file is claimed as completed output.

The qualified launcher still must start the complete source entry/capsule with
these prepared roots, preserve read-only input mounts and private output rights,
provide a protected observer, enforce real resource limits and return truthful
waits. BUILD ONLY engineering controls replace that native leaf with explicitly
inert code. They do not close any of the 32 scientific/native gates.

## V6 exact payload cap and positive EOF observation

The existing invocation payload ceiling remains unchanged: the sum of returned
stdout and stderr payload bytes may be at most output_cap. Before process birth,
the original Budget separately reserves output_cap bytes for worker-pipes and
one byte for worker-pipe-eof-probe. This additional observation headroom uses
the same finite original read budget; inability to reserve it refuses before
birth. No profile or output ceiling is increased. Journal request reservations
and the immutable runtime call state both quantities explicitly.

The controller reads at most remaining payload capacity until it reaches the
ceiling. It then performs a positive one-byte read on each ready remaining pipe.
An empty return establishes that pipe's EOF and acknowledges zero bytes. The
first nonempty probe byte establishes overflow, is charged to the probe token,
and immediately refuses worker-pipe-cap without entering returned payload or
a successful receipt. BlockingIOError acknowledges no bytes and leaves the
original reservation pending. Any other read error stops the loop, preserves
the raw first object and marks the active read reservation's possible prefix
unknown. No zero-length read is used as evidence of EOF.

The single probe reservation suffices because this owner executes all pipe reads
serially: a returned byte or ambiguous probe exits before another probe can
consume capacity. A zero-byte EOF or explicit BlockingIOError consumes none.
Both acquired pipes still receive independent once-only cleanup and both read
reservations receive independent once-only settlement. Payload and probe
acknowledgements and uncertainty remain distinct; total acknowledged bytes
include a refused overflow byte. Original close/accounting/settlement failures
remain ordered under the same source-owned Custody, with no retries or refunds
after ambiguity. Both actual positive-size EOF observations and the original
wait are required before result publication. The original receipt retains
pipe_observation with the exact cap, probe capacity, acknowledgements and EOFs.

This repairs a functional exact-ceiling boundary. It does not qualify the native
launcher, claim a production exploit, change scientific mathematics, or close
any of the 32 scientific/native gates.
