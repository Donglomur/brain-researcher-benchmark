# Original task preparation, collection and recovery

This component connects the authenticated original store, permitted-input cache, explicitly selected candidate provider and original scorer. It is the full reproduction option: 14 sessions, eight people, 58,926 source jobs, 6,776,076 held-sentence software callbacks and 224 result arrays. The separately adopted Figure 3b improvement endpoint has its own selector and needs its own correctly scoped store/collector. This full runner refuses to relabel its engineering-fixture mode as that scientific task.

`prepare.py` is the actual-data preparation entrypoint. It takes an exact external admission file and SHA, verifies the admitted producer source, and calls that producer's independently guarded archive/preparation/census route. It performs no model or native-provider execution. A future operator must separately reserve output storage and enforce the whole-stage deadline and RAM profile. It loads the exact producer, reader, coordinator and provider sources, binds a globally frozen candidate and information condition, and checks complete schedule and additive operator resource allowances. The provider mode must be explicitly chosen and separately qualified. There is no default practical native launcher, Mac fallback, paid API connection or automatic installation.

`collect()` streams one session and one source job at a time. It freezes every held request, writes exact private evaluation records, stages one selected feature per job, dispatches only that request's permitted response/maps bundle, requires provider closure and collects predictions in original row order. The whole-stage deadline is not reset per query. All owned resources receive cleanup attempts even if an earlier close fails. Failed runs preserve partial files and a bounded failure receipt; completion is published only after owned cleanup succeeds.

Two private authority streams retain canonical per-job metadata and 88-byte held-request records. They preserve exact request IDs and original frozen-authority JSON without copying qid/time maps per job. Those maps are recovered from the separately authenticated store. Full reproduction requires at most 596,294,688 request-record bytes plus 483,193,200 bounded metadata-frame bytes, before the small enclosing receipts. These are additional to the packed prediction products. Recovery authenticates both streams, rereads bounded job frames with explicit accounting, reconstructs the exact original authority trace and uses the unchanged packed reader and pooled Pearson scorer. It does not rerun a candidate or rebuild every bundle.

`recover()` writes all 224 original-format result arrays. Its explicit full-summary mode also invokes the unchanged source reducer, including the original nine permutation comparisons and context curve fit under declared numerical versions. This is future scientific work; generated controls do not execute it. Recovery has a whole-stage deadline check around jobs, summary and output boundaries; an external hard timeout must also bound indivisible numerical calls.

Preparation and collection remain distinct. The full input-store proposal is approximately 3.93 GB of bounded logical content and 220,317 files; it has not been created or allocated here. The original full callback schedule entails about 2.22 TB of logical response/maps delivery and 3.49 TB of feature visibility, with actual copying dependent on the provider. The cache constructor alone needs 323,272,704 bytes for the largest proposed full session. Separate cache, reader, collector, recovery, runtime and participant allowances must be added; per-component limits are not a single process-RSS bound. Neither ideal cache reuse nor native campaign practicality is qualified.

Fresh native processes are one isolation mechanism, not a scientific requirement or an API-call count. Any optimized callback, clean supervisor or resettable runtime must preserve the original training exclusions and declared candidate expressivity. A persistent arbitrary-code callback may accumulate another fold's held responses; the private coordinator must never be its fork ancestor. The explicit exec-reset provider remains an unqualified baseline option until actual platform, namespace, cgroup, descriptor and lifecycle evidence is admitted.
