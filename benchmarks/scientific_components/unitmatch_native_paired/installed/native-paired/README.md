# UnitMatch: native reference and paired five-mouse comparison
Public profile `unitmatch_native_paired_public_local_socket_v1` changes only source packaging, source identities and the unused legacy Docker default; scientific function bodies remain unchanged. The complete ordinary dependency tree is mirrored under the package's `source_repository/`. Its live manifest and this study's runner-manifest pin identify the new profile. See the [public package guide](../../README.md) for the usable source-only command, notices and external requirements. Historical private construction logs are excluded.

This is a build-only successor for `PAPER-paper-method-007`. `study.py` owns an actual MATLAB reference launch, ten isolated candidate outputs, the target-last release, retained functional products and the paired report. It does not accept a baseline file or a pluggable native provider. No MATLAB or authentic-data study was run to construct this source.

The scope is the original five mice, two recordings per mouse, 1,264 recorded good units, and complete directed probability matrices of sizes 534, 109, 96, 59 and 466. Each method has 526,890 entries, including diagonals and both directions. The native method plus A and B therefore contribute 1,580,670 entries. Native input preparation retains all 3,836 recorded waveform files and ten channel arrays, including waveforms beyond the good-unit selection; the original Good_ID metadata alone determines the scoring roster. This is a claim-specific functional-proxy benchmark, not reproduction of the paper's full 16-mouse study or a measurement of true neuron identity accuracy.

4. Capture all native and ten candidate products, validate the original full submission interface, recheck both sealed programs, and write `TARGET_LAST_BARRIER.json`. There is one operational functional-target read site, after this barrier. A late B failure cannot open the private grading targets. 5. Verify the same open PreparedData objects, retain the raw spike/time-template products, join the original good-unit identities, and compute both directed split-half banks. Retain histogram mass accounting, exact edges, both complete correlation matrices and both score-bank outputs per mouse. Every definedness/count/identity must agree exactly, with the frozen numerical engineering tolerance for finite arithmetic. A disagreement refuses the comparison; it is not normalized away.
6. Emit an all-five report. A and B separately improve on native only when all five candidate/native mouse endpoints are eligible, the candidate strictly improves equal-mouse mean AUC, and every mouse has nondecreasing decoded match count and finite matched-direction count. Eligibility remains at least 20 matches, 40 finite matched directions and defined AUC. No missing-mouse mean is emitted. B−A reports signed per-mouse effects and descriptive five-mouse dispersion/standard error, without neuron-pooled significance.

## Functional independence and retained dependencies

`reference-bank-v1/reference_bank.py` is a separately expressed arithmetic bank for the frozen mathematical contract. The producer keeps the original NumPy histogram/centering/dot-product recipe and loads the unchanged original decoder/rank-AUC/score source. The separate bank uses standard-library bin searches, separately centered correlations, exact tie-count AUC and independent greedy matching. Their original construction outcomes are not part of this public source package.

Both banks share the captured spike arrays, original cohort identities, the admitted 42 binary64 edges and candidate probabilities. The raw HDF5 parser and public metadata custody are shared dependencies; independent arithmetic is not independent data provenance. The producer's NumPy selection is also compared against a separately expressed scalar join from the retained raw arrays. The comparison requires exact decoder-pair identities, support counts and definedness, with tolerance-bounded finite correlation and score agreement. It does not compare rank or tie structures directly; rank changes can cancel in AUC or remain within that engineering tolerance. No historical/native numerical tolerance is inferred from the engineering tolerance.

The HDF5 admission additionally requires finite integral template labels and ordinary numeric dtypes no wider than eight bytes. Invalid inputs are refused; there is no imputation, sorting, label aliasing, renumbering or scientific repair. Full per-mouse spike, retained-product and live-payload envelopes must be chosen prospectively. The full raw arrays and products remain private evaluation artifacts, never source transport/public files.

## Future runtime invocation and genuine gates

The entry is ordinary Python source and accepts explicit paths. Use a canonical, unlinked Python executable path; a Homebrew symlink must be resolved by the operator. No source install is necessary to inspect or import the pure source. Invocation shape:

```text
python3 -I -B study.py --repository REPOSITORY --package ORIGINAL_UNITMATCH_PACKAGE
  --source-sha256 ACCEPTED_SOURCE_BINDING_SHA256 --program-a PROGRAM_A.py --program-b PROGRAM_B.py
  --method-a NAME_A --method-b NAME_B --policies POLICIES.json --limits SELECTED_LIMITS.json
  --python CANONICAL_PYTHON --matlab CANONICAL_MATLAB --docker CANONICAL_DOCKER
  --docker-host unix://SELECTED_DAEMON --docker-config SELECTED_CONFIG --output FRESH_PRIVATE_DIRECTORY
```

`POLICIES_TEMPLATE.json` describes required declarations; unfilled `REPLACE:` values are refused. `LIMITS_TEMPLATE.json` deliberately contains unresolved values, so it cannot accidentally admit a run. It includes separately selected MATLAB, Python and Docker executable identities, checked around their actual use. Those trusted-operator identities are not independent proof that a binary is genuine or an environment qualified. The actual source-owned native implementation and grader are complete; a template is not a replacement native provider. A future operator must select genuine environment, rights/access, storage and runtime operands before execution.

Real MATLAB and applicable licensed toolboxes remain external requirements. The historical source recipe names MATLAB R2022a with System Identification, Signal Processing, Image Processing and Statistics/Machine Learning toolboxes; optional parallel components are distinct. This build has not established a working MATLAB installation, toolbox/dependency resolution, native numerical equivalence or sufficient full-study resources. The native adapter records observed process/toolchain/source resolutions; these observations alone do not establish license entitlement or full transitive closure. Resource counters bound controlled reads/writes and stream capture; they do not substitute for an operating-system quota on MATLAB. Arbitrary native outputs or survivors can fail admission, and failed products are retained rather than promoted.

The original two candidate arms reserve 80 GB controlled reads, 26 GB writes and 6 GB retained capacity in aggregate, before native staging, native products, functional products, streams, manifests and headroom. These are conservative declared envelopes, not measured requirements or fresh availability. The old 2,464,443,768-byte data declaration is historical evidence only. No acquisition, native qualification, installation, empirical improvement, readiness or benchmark-count promotion follows from this source.

Public-data exposure remains a study limitation. Fresh candidate containers and sealed methods constrain this attempt; they cannot prove the model never encountered the public files or author code before the study. The code-access comparison needs separately assessed method/provenance declarations and equal non-code resources.
