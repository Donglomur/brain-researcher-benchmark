# Finite sleep workflow comparison

This additive source composes the original registered programme interface, the
accepted complete scripted viewer collection, and a fresh protected paired
grade. Its panel is **two exposed development people, 2,780 + 2,670 = 5,450
30-second epochs**. One fixed uniform-programme construction run has completed
on the original inputs, with independently checked saved evidence. Both full
programme outputs passed protected paired grading against the accepted
historical scripted-viewer output. There are no AI results here. See
[`CONSTRUCTION_RECEIPT.json`](CONSTRUCTION_RECEIPT.json) for the exact source
and evidence identities.

The question is whether a complete prediction programme can outperform the
viewer submission on the same full panel. This is a **workflow-capability
comparison**: the raw viewer receives rendered signals without training labels,
whereas the programme receives six labeled training people (16,290 epochs),
engineered signal/clock features and saved YASA outputs. Their information
budgets differ. A difference cannot establish a causal effect of tools alone or
native neural understanding. The separate 78-person/153-night design is not
replaced or qualified by this component.

## What runs

1. `workflow.freeze` authenticates the workflow and original source, then
   freezes one ordinary UTF-8 Python file of at most 200,000 bytes and the exact
   participant image/dependency definition. It creates a new private directory
   and never opens scientific input contents. The participant code is a whole
   single-file submission; additional candidate code, mutable packages or
   undeclared weights cannot be mounted.
2. The operator separately binds and reviews the two exact exposures. Each
   includes the same 18 training arrays and two public helper files, only the
   active person's feature/YASA arrays, its original case contract and public
   validator, and frozen programme/wrapper source. Development targets,
   comparators, the other development person and the Docker socket are absent
   from participant mounts.
3. `workflow.execute` calls the existing canonical Provider for two sequential
   `held_attempt` phases. `producer.py` invokes the original ABI:
   `python -I -B /program/program.py --input /input --out /output`. The original
   output is one stored `predictions.npz` per person, at most 400,000 bytes.
   The wrapper adds `RESULT.json` and `OUTPUTS.json` for transport capture; its
   statements never substitute for external closure evidence.
4. The Provider removes each participant producer before capture, then closes
   its holder and volume and reaps its owned CLI children. The coordinator
   authenticates and independently observes both receipts, binds all source,
   input/output, resource and clock identities, and commits both captured
   predictions. The next person starts only after the previous closure passes.
5. The coordinator authenticates the already accepted viewer proof without
   replaying or rerendering it. The original validator checks the complete
   viewer, both programme parts, and the exact original YASA/RF references.
   A fresh trusted grader repeats this admission. Only then does its one target
   loader open the private-location manifest and the original three private
   files. Participant code is never imported by either trusted process.

`grading.py` joins the two validated programme people in memory. It does not
normalize probabilities, convert precision, drop epochs, or create a new
numeric scorer. The pinned original adapter supplies target validation,
five-class macro-F1, equal-person weighting, first-class ties, private unscored
masks, supported-class balanced accuracy and signed differences. The report
retains both arms, both references, programme-minus-viewer and all four
arm-minus-reference differences. No statistical significance, population
inference, binary scientific success or SOTA claim is assigned.
