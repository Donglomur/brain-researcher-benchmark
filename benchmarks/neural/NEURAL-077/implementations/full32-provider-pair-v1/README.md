# Full32 direct-provider and frozen-programme pair

This additive component supplies a study producer and separate provider-arm admission for the existing NEURAL-077 full32 condition. It retains the scientific projection, private participant join and metrics in [full32-paired-benchmark-v1](../full32-paired-benchmark-v1/README.md). The original 400-case provider route and the old full32 local-driver admission remain unchanged.

The comparison is direct numerical observation versus a separately frozen numerical programme. It is not an adaptive tool-agent condition. Source controls use generated fixtures; this component has made no live provider/model calls, opened no original EEG payloads and produced no scientific score. The previously accepted [6,400 fixed-canary delivery](../../docs/full6400-numerical-delivery-20261119.md) exercised its own fixed-response route, not this new adapter or a real model comparison.

The evaluation cohort remains participants 008, 009 and 011–040: 32 people with 200 event-locked queries each. Training participants 001–006 and the previously exposed development pair 007/010 are excluded. This is separation within the local study, not evidence that a pretrained model has never seen this public dataset. The frozen authoring-exposure declaration records known access; it cannot prove an author's hidden lifetime exposure.

Each arm receives the same four complete labeled demonstrations and one complete query: Cz and Pz, 1,024 samples each, in round-trip decimal serialization. Only the explicit permission sentence differs. Projection excludes the staging roster, source times, participant grouping, private answers and other queries. The condition forbids an extra training feature bank or fitted coefficient set, and the projected prompt exposes neither. The captured bundle and exposure declaration support operator audit; generic frozen Python can embed constants, so these records do not prove that hidden learned coefficients are absent. No prompt truncation, replacement demonstrations, pooled evaluation learning or inter-query feedback is allowed. A future operator must provision the selected backend for the complete input; a byte ceiling is not a tokenizer-capacity guarantee.

The answer is experimental target versus standard event identity. It is not a physiological P3-presence annotation. The released-marker epoch coordinates, native amplitude units, lack of added shift/filter/trial rejection and unresolved physical 26-ms calibration remain unchanged. The model's general scientific knowledge is not a new source of ground-truth labels or a claim that all neural nuisance explanations have been eliminated.

## Freeze, capture and admit

Before these entrypoints open a PacketSession or query context, they freeze the selected model/output allocation, complete programme bundle, adapter/dependency identities, budgets and authoring-exposure declaration. This ordering does not prove an author’s lifetime lack of query exposure. An accepted complete arm binds the same freeze. Source or configuration drift, duplicate provider response identities, retries, truncated frames, altered first responses and incomplete or misaligned arms are refusal conditions.

The direct route uses a trusted operator broker with credentials delivered through an anonymous pipe, reusing the existing bounded HTTPS sender/custody primitives. The participant sees only the complete projected prompt and response contract. The broker retains the original request/response bodies and bounded HTTP/bridge evidence. Admission reconstructs the exact selected request, verifies the original first answer and joins the captured response to the selected model, policy, context and closure. A generic `END.json` assertion or a self-reported policy flag cannot qualify a provider.

The programme route executes the selected frozen bundle in fresh restricted processes and retains complete framed inputs, original first responses and owned closure records. A meaningful non-canary programme is a requirement of a later scientific study; the generic runner cannot prove that a selected programme is meaningful. Its admission does not inherit the fixed-canary `0.5` success predicate. Programme evidence uses the existing full32 public-arm contract; provider evidence is admitted separately rather than relabeled as a legacy local-driver run.

Captured policy consistency, trusted-broker custody and known local process closure have explicit limits. They do not prove a remote server's hidden context or tool behavior, credential memory erasure, adversarial host security, escaped-descendant containment or live backend capacity. Provider/context qualification remains explicit and is not promoted by generated fixtures or consistent receipt fields.

## Protected evaluation

Both full arms must contain exactly the same 6,400 queries and must pass public admission and closure checks before even the private-material descriptor is opened. Evaluation never imports or executes candidate code. It reuses the existing private join and equal-participant balanced accuracy at `p >= 0.5`, natural-log loss with metric-only clipping at `1e-15`, and direct-minus-program paired differences. No new target definition or pass threshold is introduced.

A completed real result can be summarized by the separately frozen [paired-participant bootstrap](../full32-paired-bootstrap-v1/README.md). Trials are not independent participant replicates. Scientific reporting requires actual independently answered arms and protected grading evidence; this source contribution supplies no accuracy, bootstrap interval, improvement or SOTA claim.

## Operator entrypoints

The following commands describe a later, separately selected study. Use exact byte counts and SHA-256 values for the selected specification and resulting contract; paths are trusted operator operands. The specification contains exactly `schema`, `public_root`, `public_manifest`, `provider`, `programme_root`, `programme_manifest`, `authoring_exposure`, `interpreter`, `sandbox` and `limits`. Its schema is `erp-full32-provider-pair-freeze-spec-v1`. The provider record fixes `model` and `max_output_tokens`; the programme manifest and exposure document have explicit path/byte/hash descriptors. See `freeze`, `validate_contract` and `validate_exposure` in [pair.py](pair.py) for the exact bounded field contracts.

```text
python -I -B pair.py freeze \
  --spec SPEC.json --spec-bytes SPEC_BYTES --spec-sha256 SPEC_SHA256 \
  --output NEW_FREEZE_ROOT

python -I -B pair.py run-arm \
  --contract NEW_FREEZE_ROOT/CONTRACT.json \
  --contract-bytes CONTRACT_BYTES --contract-sha256 CONTRACT_SHA256 \
  --condition numeric_direct_four_demo --output NEW_DIRECT_ARM \
  --credential-fd 3

python -I -B pair.py run-arm \
  --contract NEW_FREEZE_ROOT/CONTRACT.json \
  --contract-bytes CONTRACT_BYTES --contract-sha256 CONTRACT_SHA256 \
  --condition numeric_program_four_demo --output NEW_PROGRAMME_ARM

python -I -B pair.py evaluate \
  --contract NEW_FREEZE_ROOT/CONTRACT.json \
  --contract-bytes CONTRACT_BYTES --contract-sha256 CONTRACT_SHA256 \
  --arms PUBLIC_ARMS.json --private-material PRIVATE_MATERIAL.json \
  --output NEW_EVALUATION
```

`freeze` creates `PROGRAMME.json`, `EXPOSURE.json` and `CONTRACT.json` without opening query records. The direct credential descriptor must already be an inherited anonymous pipe provisioned by an authorized operator application; writing `3` in a command does not create credentials or authorize spending. Never put credentials in command-line values, configuration files or retained request data. The programme arm receives no credential descriptor. The programme is an operator-selected complete frozen bundle; this component does not automatically select a competent method or a canary.

`evaluate` performs admission internally; there is no standalone admission CLI. The public-arms JSON selects the two exact condition roots and receipt byte/hash descriptors. Its private-material pathname is deliberately lazy: it is not resolved, inspected or opened until both complete arms pass. Keep all outputs fresh and disjoint from selected source, authoring and protected packet trees.

## Runtime and verification scope

Source compilation and generated controls use the selected Python 3.11.6 interpreter and the standard library. The programme interpreter is a separate, explicitly frozen execution operand. The unchanged macOS sandbox supports its existing system/Python-framework scopes and does not grant Homebrew `/opt` access. Selecting the source-control interpreter for a future programme run does not qualify it for that sandbox; unsupported runtime paths are refused before query access. No sandbox policy is broadened here.

The focused generated controls exercise the new request/response and admission boundaries, including altered requests/responses, incomplete evidence, duplicate/retried answers and changed pre-query commitments. They do not replay the 6,400-case delivery or start live model clients. Public tests support an external `ARTIFACT_DIR`; fixture/output locations must be disjoint from the source and dependency trees and remain within finite bounds. The exact observed control count, command, runtime identities and any preserved initial mismatch are recorded in the final source metadata.

A later live study requires its own authenticated provider connection, spending and resource selection, full-input capacity and trusted capture custody. The source-control grant is not a study allocation. Finite request/episode/campaign and byte limits are refusal bounds, not demonstrated adequacy for 6,400 model requests. Local closure does not establish remote cancellation or cessation of remote billing. Source construction and these documented entrypoints do not authorize execution.
