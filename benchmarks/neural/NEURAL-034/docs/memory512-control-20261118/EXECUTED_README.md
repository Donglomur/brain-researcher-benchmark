# NEURAL-034 proposed 512 MiB viewer-grade profile

This additive successor grades the same already-closed seven-fold, 140-row
combined calcium/behavior viewer collection. It preserves the original image,
grader and score source bytes, six reference streams, equal-mouse metrics,
two CPU/two-thread worker, immutable snapshot, offline read-only isolation,
new process owner, original cleanup, and 7/8.5-second worker timing. It changes
the explicit protected RAM and RAM+swap ceilings from 4 GiB to 512 MiB and the
cooperative host request from 6 GiB to 2 GiB. Neither proposed ceiling is
measured sufficient. The old package, proposal, HOLD and reservation remain
historical and unchanged; no qualification transfers to this overlay.

All 55 accepted configured source files retain manifest 498cd4c2 and freeze
e8de8629. A separately pinned overlay derives only the resource verifier,
finite worker dispatch, telemetry capture and terminal-record ordering from
those authenticated bytes. Both grade and post-owner recovery select the same
derived runtime. Root must bind the exact new profile and eligibility record;
an old 4 GiB qualification is refused. Proposal files never authorize execution.

The new read-only telemetry entrypoint authenticates and calls the unchanged
original grader. Raw stderr frames and normalized original streams are both
saved and joined. Kernel memory.peak (v2) or memory.max_usage_in_bytes (v1)
reports a high-water value through its recorded read cutoff, not through all
later output and container exit. OOM counters and Docker's actual terminal
OOMKilled/exit state are distinct evidence. A missing final frame, unsupported
kernel counter or failed worker is retained as incomplete/unknown; process RSS,
Docker samples and exit137 are never substituted for a true peak/OOM finding.
Two frames alone do not establish supported memory evidence.

The original bounded host command capture is reused for before/after vm_stat
and pressure-level observations within the same 90-second watchdog plus
5-second kill grace. These observations neither cap the Docker VM nor establish
healthy pressure, swap stability or root admission. The exact container ID is
inspected before cleanup on failure when time remains; a running state is not
called a terminal exit. Timers and strict cleanup remain authoritative.

No authentic data, Docker operation, participant, model, fit or protected grade
has been executed for this successor. A separately admitted fixed0.5 control
must establish its actual operational behavior. The selected exposed seven-mouse
development panel, calcium+behavior representation and absent provider/model
qualification remain explicit. This is one task condition, not a new benchmark.
